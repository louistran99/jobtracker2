Job Application Tracker: design

Screens: a list of applications, a detail and edit screen, a summary of counts per stage, and a sheet for adding an application. The screens are iPhone 16 Pro size (393 × 852 pt) and follow stock iOS conventions. The notes under each screen list the SwiftUI topics that screen lets you talk about in an interview.

Design direction

Native: built from stock SwiftUI

Uses system components wherever possible: NavigationStack, inset-grouped List, Form, and a TabView with two tabs. Most of the UI comes from standard components, so you write little custom layout. That leaves the conversation on state, data flow, and persistence instead of styling.

  • Swift Charts: a BarMark per stage with .foregroundStyle(by: .value("Stage", …)) and .annotation(position: .top) to show the count above each bar.

Adding an application

Tapping "+" on the Applications screen (A1) opens a full-height sheet. Pasting a job link is the fastest way in: the app fetches the posting and fills in the company and role. Every field can still be typed by hand, and only company and role are required.

  1. A4: the sheet opens with the cursor in the link field and the URL keyboard up. "Add" stays disabled until company and role are filled.
  2. A5: after a paste, the posting is fetched, the company and role are filled in, and "Add" becomes available.
  3. A6: the link field's four possible states: fetching, found, couldn't read the posting, and already added.

  • Draft, not a model: the sheet edits an ApplicationDraft struct held in @State. A SwiftData model is created only when you tap Add, so Cancel has nothing to roll back. Expect a "why not insert and delete on cancel?" question.
  • Focus: @FocusState puts the cursor in the link field when the sheet opens, with .keyboardType(.URL) and autocapitalization turned off.
  • Validation: draft.isValid controls whether Add is enabled. It is a pure function and an easy first unit test.
  • Accidental dismiss: once the draft has changes, .interactiveDismissDisabled(draft.isDirty) blocks swipe-to-dismiss, and Cancel asks "Discard this application?"

  • Async fetch: .task(id: draft.postingURL) waits about 300 ms, then calls a PostingMetadataService actor. When the URL changes, SwiftUI cancels the previous fetch, which handles both debounce and cancellation.
  • Autofill rule: fetched values never overwrite a field you have already typed in, and the footnote under Details only mentions fields that still hold fetched values. It's a small rule that's easy to test and to discuss as a product decision.
  • Sensible defaults: Stage starts at Applied and the date at today. The next-step fields appear only when the toggle is on, so the common case takes one paste and one tap.
  • After Add: the sheet closes and the new row appears in A1 through @Query, with no manual refresh.

  • One enum: FetchState has the cases .idle, .loading, .loaded(PostingMetadata), .failed, and .duplicate(addedOn: Date). Because the cases can't overlap, the view can't show conflicting states such as loading and error together.
  • Failure isn't a blocker: if the fetch fails, the form keeps working. Many job sites block scraping, so manual entry has to be a normal path, not a dead end.
  • Duplicates: before fetching, the app normalizes the URL (removing tracking parameters) and checks it with a #Predicate query. This check runs locally, so it's fast and works offline.
  • VoiceOver: each state change is announced with AccessibilityNotification.Announcement, so screen-reader users find out when the fields have been filled.
