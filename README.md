# Job Tracker

An iOS app for tracking job applications, from applying through to an offer.
Designs are in [`mockups/`](mockups/job-tracker.html) (epic KAN-60).

## Getting started

Requirements: Xcode 26 or later. No other tools are needed: everything else
is pinned and installed into `.tools/` on first use.

```sh
make open      # generate JobTracker.xcodeproj and open it in Xcode
make check     # lint + unit tests + UI tests, the same as CI
```

| Command          | What it does |
|------------------|--------------|
| `make generate`  | Generate `JobTracker.xcodeproj` from `project.yml` (run after pulling or editing `project.yml`) |
| `make format`    | Format all Swift code in place |
| `make lint`      | Check formatting and lint rules; any finding fails |
| `make test`      | Unit tests |
| `make ui-test`   | UI tests |

The Xcode project is generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen)
and isn't committed. Edit `project.yml`, never the project itself.

To hunt for flaky tests:
`make test TEST_FLAGS='-test-iterations 20 -run-tests-until-failure'`.

## Architecture

MVVM with a single in-memory store. Layers are separate Swift package
modules, so the compiler enforces the boundaries.

```
View (SwiftUI, no logic)
  └─ ViewModel (@Observable, @MainActor, dependencies passed to init)
       └─ ApplicationStore (single source of truth, shared by every screen)
            └─ ApplicationRepository (protocol)
                 ├─ JSONFileApplicationRepository (app)
                 └─ InMemoryApplicationRepository (previews, tests, UI tests)
```

| Module (`Packages/JobTrackerKit`) | Contents | Depends on |
|---|---|---|
| `Domain` | Value types (`Application`, `Stage`, `ApplicationDraft`), pure logic (`PipelineStats`), the repository protocol. Foundation only. | — |
| `Storage` | `JSONFileApplicationRepository` | Domain |
| `DesignSystem` | Stage colors, `CompanyAvatar`, `StageBadge`, `StagePicker`, `FormFieldRow`, `StatTile`, `IconTile` | Domain |
| `Features` | `ApplicationStore`, then one folder per screen with its view and view model | Domain, DesignSystem |

The app target (`App/`) is the composition root. `AppDependencies` is the only
place that picks concrete implementations. Launching with `-ui-testing` swaps
in seeded in-memory storage and turns off animations, so UI tests are
deterministic.

Conventions:

- **Views hold no logic.** They render view model state and forward user actions.
- **View models get every dependency through `init`,** including the clock
  (`now`) and ID generation, so tests control them. There are no singletons.
- **Business rules are pure functions on value types in `Domain`,** tested
  without any UI or storage.
- **Edits work on drafts.** A form edits a value (`ApplicationDraft`), so
  Cancel never has to undo anything in storage.
- **Errors are never swallowed.** Failed loads and saves are shown to the user.

Decisions are recorded in [`docs/adr`](docs/adr).

## Testing

- Unit tests use [Swift Testing](https://developer.apple.com/documentation/testing),
  live next to each module in `Packages/JobTrackerKit/Tests`, and run in parallel.
- UI tests (`UITests/`) cover the main flows against seeded in-memory data.
- Swift 6 language mode, and warnings are errors.
